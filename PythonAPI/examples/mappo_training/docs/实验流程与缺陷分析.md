## 1. TL;DR — 一页纸结论

| 维度 | 现状 | 问题 | 行动 |
|---|---|---|---|
| **已有能力** | MAPPO + CTDE + 8 场景 + v2 连续奖励 + 软课程 + 单对抗 PPO | 系统能跑通 | — |
| **实验严谨度** | 单 seed、训练集=测试集、无 baseline 对照 | **无法支撑"v2 比 v1 好"这种结论** | Phase 1, 2 |
| **泛化能力** | 训了 8 个直道场景；唯一变量是起点 | 没有验证泛化（hold-out、新地图） | Phase 5 |
| **对抗鲁棒性** | 训对抗 agent 时合作策略冻结 | 没有 co-evolution，对抗强度上限有限 | Phase 4 |
| **已知 bug** | `ep_success` 把 timeout 当成功；severe collision 全员 done 影响信用分配；reward 量级失衡 | 指标失真 + 信用分配模糊 | 立即修 |
| **算法多样性** | 仅 MAPPO；无 IPPO/QMIX/MADDPG 对照 | "MAPPO 在此任务最优"这一结论无证据 | Phase 6 |

> 一句话：**当前管线工程完整度高，但实验方法学薄弱**。在跑大规模训练前，先补齐三块短板：metric 正确性、基线对照、训练/测试集分离。

## 2. 实验目标层级

```
┌── L0：系统跑得通 ────────────────────────── ✅ 已达成
│   能完整训练 → 保存 ckpt → 评估出数字
│
├── L1：能稳定学到合理策略 ──────────────── ✅ 大致达成
│   碰撞率持续下降，成功率持续上升
│
├── L2：v2 改造（奖励 + 鲁棒训练）有效 ───── 🟡 待验证
│   v2 在控制实验下显著优于 v1
│
├── L3：策略具备泛化能力 ──────────────────── 🔴 未开展
│   在训练时未见过的场景上仍能完成任务
│
├── L4：对抗鲁棒性 ─────────────────────────── 🟡 部分
│   面对策略性对抗 agent 仍能维持安全
│
└── L5：算法层面有贡献 ───────────────────── 🔴 未开展
    与 IPPO/MADDPG/QMIX 等基线对照后，
    MAPPO 在此设定下展现明确优势/特性
```

后续每个阶段对应攀升一个 Level。

## 3. 推荐实验流程（六阶段）

### Phase 0：修 bug + 重建基线（**先做**，预计 1-2 天）

**目标**：把已知的指标失真和明显 bug 修了，再开任何新实验。

**任务清单**：
- [ ] 修复 `ep_success` 误判（[§4.1](#41-bug-ep_success-把-timeout-错算成成功)）
- [ ] severe-collision 全员 done 时，写入 per-agent `truncated_by_other` flag（[§4.2](#42-severe-collision-全员-done-污染信用分配)）
- [ ] 增加 `--seed` 至少 3 个独立 seed，TB 路径以 seed 区分
- [ ] 增加 `episode/success_rate_to_goal`（真正到终点的比例）和 `episode/collision_rate` 两个独立指标，不再用"非碰撞=成功"
- [ ] checkpoint 选择策略：维护一个 `best_ckpt`（按窗口 success_rate_to_goal 取 max），而不是只看最后一个

**通过标准**：跑一个 50-update 的 sanity run，TB 上能看到三类终止（success / collision / timeout）分别的占比。

---

### Phase 1：固定 baseline（预计 2-3 天）

**目标**：建立"什么都不做"的对照基线，作为后续所有改造的对比锚点。

**变量矩阵**：

| 实验 ID | 算法 | 奖励 | 场景 | 课程 | 采样 | 主要观察 |
|---|---|---|---|---|---|---|
| `B0_random` | 随机策略 | — | scenario_01_basic | — | — | 任务难度下界 |
| `B1_single_v1` | MAPPO | v1 | scenario_01_basic | 无 | — | 最简 baseline |
| `B2_single_v2` | MAPPO | v2 | scenario_01_basic | 无 | — | 看 v2 改造效果（单场景） |

每组 **3 个 seed × 200 updates**。

**输出**：一张表 + 三条 success_rate 曲线。

**通过标准**：
- B0 成功率 ≈ 0（系统正确）
- B1/B2 成功率 ≥ 60%（任务不至于太难学不会）
- B2 优于 B1（v2 在单场景下有效）

---

### Phase 2：奖励 A/B（预计 2-3 天）

**目标**：在多场景下验证 v2 奖励函数的优势。

**变量矩阵**：

| 实验 ID | 奖励 | 场景 | 课程 | 采样 |
|---|---|---|---|---|
| `R1_v1_robust` | v1 | 8 个 | 软过渡 | weighted |
| `R2_v2_robust` | v2 | 8 个 | 软过渡 | weighted |

每组 3 seed × 300 updates。

**对比工具**：现成的 [`compare_reward_versions.py`](../evaluation/compare_reward_versions.py)。

**通过标准**（["7.5 判断优化有效的标准"](reward_optimization_plan.md)）：
- v2 碰撞率 < v1 同期
- v2 平均速度不显著降低（< 15% 下降）
- v2 episode return 收敛更快或更高

---

### Phase 3：Robust v1 vs v2 训练流（预计 2-3 天）

**目标**：把 changelog 里宣称的 v2 训练流改进**用实验验证**。

**变量矩阵**（控制其他变量，只变训练脚本）：

| 实验 ID | 训练脚本 | rollout_ep | ppo_ep | GAE | 采样 | 软过渡 |
|---|---|---|---|---|---|---|
| `T1_v1` | robust v1 | 4 | 10 | 全局 | random | 否 |
| `T2_v2_pure` | robust v2 | 16 | 5 | per-ep | weighted | 是 |
| `T3_v2_minus_gae` | robust v2 | 16 | 5 | **全局** | weighted | 是 |
| `T4_v2_minus_curr` | robust v2 | 16 | 5 | per-ep | weighted | **否** |
| `T5_v2_minus_sampling` | robust v2 | 16 | 5 | per-ep | **random** | 是 |

**做消融实验**——把 v2 的每个改动单独剥离，看哪个改动贡献最大。

**通过标准**：T2 > T1，且 T3/T4/T5 各自比 T2 差，证明每个改动都有正向贡献。

---

### Phase 4：对抗训练（预计 3-5 天）

**目标**：用 Phase 3 选出的最佳 ckpt 作为预训练，训出能稳定干扰的对抗 agent，再观察合作 agent 的脆弱性。

**变量矩阵**：

| 实验 ID | 预训练 | 对抗算法 | 课程 | 评估 |
|---|---|---|---|---|
| `A1_baseline` | T2 best | PPO（agent 2 单训） | 无 | 在 8 场景上测合作成功率下降 |
| `A2_curriculum` | T2 best | PPO + curriculum | 是 | 同上 |
| `A3_multi_adv` | T2 best | MAPPO（多对抗）| 是 | 同上 |

**关键观察**：训练前 vs 训练后合作 agent 的成功率差距 = 对抗 agent 的有效性。

**进阶（Phase 4b）**：**Co-evolution / iterative training**
```
loop k = 0..K:
  freeze adversary → train cooperative agents (M updates)
  freeze cooperative → train adversary       (N updates)
```
解决"对抗只能在固定合作策略上学"的局限。当前 [`train_adversarial_ppo.py`](../training/train_adversarial_ppo.py) 缺这一层。

---

### Phase 5：泛化评估（预计 1-2 天）

**目标**：验证策略在**训练时未见过的场景**上是否仍可用。

**任务清单**：
- [ ] 手工设计 4-6 个 held-out 场景（与训练 8 个不同的起点 / yaw / 间距分布），放到 `data/test_scenarios/`
- [ ] 修改 [`evaluate_robustness.py`](../evaluation/evaluate_robustness.py)，新增 `--test-scenarios-dir` 参数
- [ ] 跑训练集 vs 测试集对比表：success_rate / collision_rate / avg_lateral_deviation

**进阶**：在新地图（Town01、Town03）的直道上做 zero-shot 评估，看跨地图泛化。

**通过标准**：测试集成功率 ≥ 训练集成功率 × 70%（一定程度的 gap 是合理的）。

---

### Phase 6：与基线算法对照（预计 5-7 天，可选）

**目标**：在 paper / 答辩中需要"我为什么不用 X"时有数据可答。

**候选对照**：

| 算法 | 实现路径 | 主要差异 |
|---|---|---|
| **IPPO**（Independent PPO）| 把 CentralizedCritic 改成 PerAgentCritic | 去中心化训练，验证 CTDE 的价值 |
| **Shared-policy MAPPO** | 所有 agent 共享同一个 Actor | 验证 non-shared policy 的价值 |
| **MADDPG** | 需新增实现，约 1 周 | DDPG 系，连续动作经典 baseline |
| **QMIX**（离散版） | 动作离散化（throttle/steer 9 档），需新增 | 价值分解 baseline |

最少做 IPPO + Shared-policy 两个变种，工程量小且能说明问题。

## 4. 当前实验的核心缺陷

按"bug / 实验设计 / 算法设计 / 工程"四类分组。

### 4.1【Bug】`ep_success` 把 timeout 错算成功

**位置**：[train_no_rllib_mappo_robust_v2.py:591-594](../training/train_no_rllib_mappo_robust_v2.py#L591-L594)

```python
if all(dones.values()):
    ep_success = not any(info.get('collisions', {}).values())
```

**问题**：`_check_dones` 在 `current_step >= max_steps` 时也会把每个 agent 的 `done=True`（[carla_multi_agent_env.py:1409](../environment/carla_multi_agent_env.py#L1409)）。此时如果没碰撞，`any(collisions)=False` → **timeout 被算作 success**。

**影响**：
- `episode/success_rate_window` 虚高
- 课程学习的 `scenario_success_history` 被污染，"困难场景"会被错误地判定为"已掌握"，从而权重下降
- TB 上看到的成功率不可信

**修复**：
```python
# 严格定义：所有 agent 都进入 goal_zone 才算成功
ep_success = all(env.reached_target.get(aid, False) for aid in agent_ids)
ep_collision = any(
    env.collision_events.get(aid, False) or env.crosswalk_invasion_events.get(aid, False)
    for aid in agent_ids
)
ep_timeout = (ep_length >= args.max_steps) and not ep_success and not ep_collision
```

同时在 TB 上单独记录三个独立指标：
- `episode/rate_success`（到达终点比例）
- `episode/rate_collision`（碰撞终止比例）
- `episode/rate_timeout`（超时未达比例）

---

### 4.2【设计】Severe collision 全员 done 污染信用分配

**位置**：[carla_multi_agent_env.py:1437-1447](../environment/carla_multi_agent_env.py#L1437-L1447)

```python
any_severe_collision = any(
    (collision_events[i] or crosswalk_invasion_events[i]) and not reached_target[i]
    for i in range(num_agents)
)
if any_severe_collision:
    for i in range(num_agents):
        dones[i] = True
```

**问题**：agent 0 撞车 → agent 1 也被 done。MAPPO 的 -100 collision 惩罚只给到肇事方（`reward[hit_agent]=-100`），但 **agent 1 的轨迹也被截断**，未撞那侧本来可能拿到的 progress / success 都消失了，间接被"连坐"。

**影响**：
- Critic 学到的 `V(s)` 偏低（共享 global state，提前终止 → 价值低估）
- 合作 agent 学到的"防御性驾驶"策略和真实因果脱节

**修复方案**（择一）：
- **方案 A（轻）**：只对肇事 agent 设 `done=True`，其他 agent 继续。但 CARLA 场景里碰撞通常会让两车都失控，物理上继续不合理。
- **方案 B（重）**：保持当前 done 行为，但 reward 给法改成：未碰撞 agent 拿一个"被牵连"的小负奖励（如 `-10`），同时 GAE bootstrap 用其当前 `V(s)` 而不是 0，避免低估。
- **方案 C（中）**：碰撞时其他 agent reward 不动，但 GAE 计算时把它当成 **truncation 而非 termination**（done=False, bootstrap=V(s)）。

推荐 **方案 C**，对代码改动最小、语义最清晰。

---

### 4.3【设计】训练集 = 测试集

**问题**：8 个场景同时用于训练（rollout）和"评估"（[evaluate_robustness.py](../evaluation/evaluate_robustness.py) 跑同一目录）。所谓的"成功率"只能说明"在见过的起点上能不能完成"，**完全没有 generalization 证据**。

**影响**：
- 论文/答辩里写"鲁棒性评估"会被审稿挑战
- 容易过拟合到 8 个起点的具体坐标

**修复**：
- 新建 `data/test_scenarios/`，4-6 个 held-out 场景
- 评估脚本支持 `--test-only` 模式，只跑测试集

---

### 4.4【设计】缺少 baseline 对照

**问题**：所有训练都是"MAPPO + v2 + robust"或其变体，没有：
- 随机策略下界（成功率应接近 0，证明任务非平凡）
- 单 agent PPO（去掉协作维度）
- IPPO（去掉 CentralizedCritic）
- Shared-policy MAPPO（去掉 per-agent actor）

**影响**：无法回答"non-shared policy + CentralizedCritic 这个具体设计值多少"。

**修复**：见 [Phase 6](#phase-6与基线算法对照预计-5-7-天可选)。

---

### 4.5【设计】单 seed，统计意义薄弱

**问题**：所有训练脚本默认 `--seed 42`，且实验记录都只有 1 个 seed 的曲线。

**影响**：
- 看到的差异可能只是随机性
- 报告的"v2 优于 v1"在统计意义上站不住脚

**修复**：每个关键实验至少 **3 个 seed**（42, 123, 2024），TB 路径区分，绘图用 mean ± std。

---

### 4.6【设计】Reward 量级失衡

每步典型 reward：
- 正常行驶：`+8 ~ +21`（progress 主导）
- 碰撞：`-100`
- 成功：`+100 + 50·time_bonus`

**问题**：一次碰撞（`-100`）≈ 抵消 5-12 步的正常前进。但碰撞前的 50-200 步正向 reward 累积可能让 episode return 仍然偏正，**Critic 学不到"接近碰撞 = 危险"的强信号**。

**Observation**：v2 已有 LiDAR safety 和 TTC 试图缓解，但当前权重（`SAFETY_LIDAR_WEIGHT=0.3, TTC_WEIGHT=2.0`）相对碰撞 `-100` 仍然偏小。

**改进方向**：
- 引入"接近碰撞"预警 reward（如 lidar < 0.2 时大幅 ramp）
- 试 reward clipping / normalization（PPO 常见技巧）
- 或者降低 collision 绝对值到 -20，配合 done 信号已经足够告知"事件发生"

---

### 4.7【设计】对抗 agent 是"静态对手"

**问题**：[train_adversarial_ppo.py](../training/train_adversarial_ppo.py) 训练时合作 agent 0/1 **完全冻结**。对抗 agent 只能针对一个固定策略学。

**影响**：
- 对抗 agent 学到的"切入/阻挡"行为可能是针对某个特定 ckpt 的过拟合策略
- 一旦合作 agent 重训一遍，对抗 agent 大概率失效

**修复**：Co-evolution 训练流程（[Phase 4b](#phase-4对抗训练预计-3-5-天)），合作和对抗轮流冻结对方训练自己。

---

### 4.8【设计】LiDAR 探测距离 4m 太短

**位置**：[carla_multi_agent_env.py:898](../environment/carla_multi_agent_env.py#L898) 和 [L1236](../environment/carla_multi_agent_env.py#L1236)

**问题**：观测 lidar `ray_length=4.0`（约 4 米）。城市道路 30km/h ≈ 8.3m/s，4m 意味着 ≈ 0.5 秒反应时间，对训练时的避障决策窗口太小。

**修复**：
- obs 用 4m（窄视野，强制 agent 学局部决策）
- TTC 已用了 10m 前向（合理）
- 可选：obs 改为多尺度（4m × 11 ray + 15m × 5 ray 拼接），共 16 维 lidar

---

### 4.9【设计】场景多样性维度太单一

**问题**：8 个 scenario 只在起点 x/y 和 yaw 上有变化。**完全没有**：
- 时间维度（不同天气、不同时段光照）
- 其他交通参与者（NPC vehicles、行人）
- 动态突发事件（前车急刹、有车汇入）
- 不同地图（Town01/03/04…）

**影响**：训出来的策略对"无 NPC 的双车直道"以外的场景几乎一定失效。

**修复**：
- 增加 weather randomization（CARLA 原生 `set_weather` 几乎免费）
- 用 `traffic_manager.spawn_actor` 撒 N 个 NPC 车
- 起码加 1-2 个其他 town 的直道作为分布外测试

---

### 4.10【工程】Checkpoint 选择策略缺失

**问题**：所有训练脚本都按 `--save-interval` 定期存，但**没有自动跟踪"最佳"checkpoint**。评估时用 `ckpt_500.pt`（最后一个）还是 `ckpt_300.pt`（峰值）？目前靠人肉看 TB 决定。

**修复**：训练循环里维护：
```python
if window_success_rate > best_success_rate:
    best_success_rate = window_success_rate
    torch.save({...}, os.path.join(save_dir, "best.pt"))
```

### 4.11【工程】动作 mutual exclusion 在采样后做，梯度不一致

**位置**：[action_tanh_to_env](../training/train_no_rllib_mappo_robust_v2.py#L108-L121)

```python
if throttle_raw >= brake_raw:
    throttle, brake = throttle_raw, 0.0
else:
    throttle, brake = 0.0, brake_raw
```

**问题**：Actor 仍然输出 3 维（throttle, steer, brake），但 env 收到的实际是 mutually exclusive 的两个值。**Actor 的 `log_prob` 是在原始 3 维 Gaussian 上算的**，PPO ratio 计算的是采样动作的概率，不是实际应用动作的概率，这中间有一致性问题。

**影响**：理论上 PPO 仍然能学，但 brake/throttle 同时被激励的方向得不到一致的反馈信号，收敛会慢。

**修复方案**：
- **方案 A**：Actor 输出 2 维 `[longitudinal, steer]`，`longitudinal>0` 映射 throttle、`<0` 映射 brake。语义清晰，但需要重训
- **方案 B**：保持 3 维输出，但在 env 层用 throttle - brake 合成纵向控制（不做硬切分），让 PPO 看到完整可微行为

推荐 **方案 A**，是 CARLA RL 常见做法。

### 4.12【工程】环境 TB 与训练脚本 TB 双写

**位置**：env 内 `disable_tensorboard` 参数已暴露，训练脚本 v2 也设了 `True`。但仍有遗留——env 默认 `disable_tensorboard=False`，evaluate 脚本忘传时仍会双写。

**影响**：`logs/carla_training_reward/<timestamp>_worker_X/` 会堆出一堆评估期间产生的无用日志。

**修复**：env 默认改为 `disable_tensorboard=True`，仅在确实需要 env-side TB 时显式打开。

### 4.13【工程】超参数从未做 sweep

**问题**：`lr=3e-4, gamma=0.99, clip_eps=0.2, ent_coef=0.01` 全是 PPO 论文默认值，**从未在本任务上验证过这些是最优**。

**修复**：用 [Optuna / W&B Sweeps](https://optuna.readthedocs.io/) 起码 sweep `lr_actor / lr_critic / ent_coef / clip_eps` 四个，固定其他变量跑 20-30 组短训练（50 update）。

## 6. 扩展实验想法（可选）

锦上添花、不影响主线。

### 6.1 安全性度量

引入"安全 RL"概念，在评估时除了成功率/碰撞率，额外报告：
- **TTC 分布**（10/50/90 分位数）
- **最小 lidar 距离分布**
- **横向加速度峰值**（lateral jerk）

参考：[SafeRL benchmark](https://github.com/PKU-MARL/Safety-Gymnasium)

### 6.2 离线 RL 数据集化

把训练时的 rollout 全部存成 dataset（HDF5/Parquet），后续可以：
- 用 CQL / IQL 等 offline RL 算法做对照
- 训练时的状态分布做可视化（t-SNE）

### 6.3 与人类驾驶对比

[`utils/record_manual_control.py`](../utils/record_manual_control.py) 已能采人类数据；在测试场景上让人开几遍，对比指标：
- 人类成功率/碰撞率作为上界
- 人类平均速度 / 横向偏差作为驾驶质量基准

### 6.4 可解释性 — 注意力 / 显著性

- 在 19 维 obs 上算 Saliency map（input × gradient），看 agent 决策时主要看 lidar 哪几个 ray
- 验证 v2 加入 TTC 后，是否真的让 agent 更"看"前向 ray

### 6.5 多车规模拓展

当前固定 `num_agents=2`。试试 4 车、6 车，看 CentralizedCritic 维度爆炸时是否需要：
- attention-based critic
- mean-field 近似
