## 0.1 为什么用 v2 对抗脚本

v1 `train_multi_adversarial_mappo.py` 有几处会破坏实验结论的设计，v2 已修复：

| 问题                 | v1 现状                                        | 影响实验                         | v2 修复                              |
| ------------------ | -------------------------------------------- | ---------------------------- | ---------------------------------- |
| 对抗系数被压成无效          | `combined = adv + coef×(-coop)×0.01`，0.01 写死 | B1 系数 sweep 测不出差异 → RQ2 无法证伪 | 提为 `--zero-sum-coef`，去掉 ×0.01      |
| Critic 只看对抗 obs    | `get_adversarial_global_state()`             | 价值有偏、GAE 噪声大                 | 改用 `get_global_state()`（全员）        |
| 共享 joint advantage | 所有对抗 agent 同一 advantage                      | M 数量消融测不出分工 → RQ3 削弱         | per-agent advantage（各自 reward）     |
| 不采样场景              | 每 ep 默认直道起点                                  | 训练/测试分布不一致 → RQ4 受影响         | 复用 robust v2 场景采样 + 课程             |
| 评估不兼容              | `evaluate_adversarial.py` 读单数 key、硬编码单对抗     | §5.2 直接崩                     | 新建 `evaluate_multi_adversarial.py` |

## 0. 研究问题与假设

| 编号 | 研究问题 (RQ) | 假设 (H) |
|---|---|---|
| RQ1 | robust v2 的场景采样 / 奖励版本 / 课程改进，能否提升合作团队在训练场景集上的成功率与稳定性？（注：当前训练用全部 8 场景，无独立留出集；如需 hold-out 需另划分场景，见 §9） | H1：weighted 采样 + reward v2 + 课程软过渡 > random 采样 / reward v1 |
| RQ2 | 在冻结的合作团队上训练的多对抗团队，能在多大程度上降低合作团队成功率？ | H2：对抗团队可使合作成功率显著下降（effectiveness > 0），且随 `--zero-sum-coef` 增大而增强 |
| RQ3 | 对抗智能体数量 M 与课程学习，对攻击有效性的影响？ | H3：M=2 优于 M=1；课程学习使对抗训练更稳定、最终更强 |
| RQ4 | 经历"训练-被攻击"后，合作团队的鲁棒性短板在哪些场景上最明显？ | H4：训练分布外（边界/角度偏移）场景下成功率掉得最多 |

**核心评估指标（贯穿全部实验）**：

```
adversary_effectiveness = coop_success(无对抗) − coop_success(有对抗)
   值域 [0,1]，越大说明对抗团队越有效、合作团队越脆弱
```

## 1. 实验总体流程

```
阶段 P1  合作团队鲁棒训练 (robust v2)
         └─ 产出: coop_best.pt   ← 后续所有对抗实验的输入
                │
阶段 P2  对抗团队训练 (multi_adversarial_v2, 冻结 coop_best.pt)
         └─ 产出: adv_best.pt
                │
阶段 P3  鲁棒性评估
         ├─ 无对抗基线:  evaluate_robustness(coop_best.pt)
         └─ 有对抗对照:  evaluate_multi_adversarial(coop_best.pt + adv_best.pt)
                │
阶段 P4  消融与对照 (A/B 组) + 结果汇总填表
```

实验分两大组：
- **A 组**：合作团队训练消融（围绕 robust v2，回答 RQ1）
- **B 组**：对抗攻击训练消融（围绕 multi_adversarial，回答 RQ2/RQ3）
- **C 组**：鲁棒性评估（回答 RQ4，给 A/B 提供统一指标）

## 3. A 组 — 合作团队训练消融（robust v2，回答 RQ1）

统一基准超参（除被消融项外保持一致）：`--updates 100 --rollout-episodes 16 --ppo-epochs 5`。
每个实验跑 **3 个 seed (42 / 123 / 2024)**，取窗口成功率均值±标准差。

## 5. C 组 — 鲁棒性评估（回答 RQ4，产出统一对照指标）

### 5.1 无对抗基线（合作团队单独跑全场景）

对每个 A 组 ckpt 跑一次，得到"干净环境下"的成功率上限：

```powershell
python -m evaluation.evaluate_robustness `
  --checkpoint ./logs/exp/A0_baseline_seed42/best.pt `
  --num-episodes-per-scenario 5 `
  --output-file ./logs/exp/eval/A0_clean.json
```

### 5.2 有对抗对照（合作团队 + 对抗团队）

`evaluate_multi_adversarial.py` 内部对每个场景跑两遍（对抗 agent 切换"正常驾驶 / 对抗策略"），
直接输出逐场景与总体的 effectiveness，无需再手动相减：

```powershell
python -m evaluation.evaluate_multi_adversarial `
  --pretrained-ckpt ./logs/exp/A0_baseline_seed42/best.pt `
  --adversarial-ckpt ./logs/exp/B0_adv_M2_zs1_seed42/best.pt `
  --num-episodes-per-scenario 5 `
  --output-file ./logs/exp/eval/B0_attacked.json
```

> 脚本同时给出 `baseline_coop_success`（无对抗）与 `attacked_coop_success`（有对抗），
> `effectiveness = baseline − attacked`，逐场景写入 `per_scenario`、总体写入 `overall`。
> §5.1 的 `evaluate_robustness` 仍可作为合作团队"干净环境"成功率的独立交叉验证。

## 9. 注意事项

1. **隔离 save-dir**：每个实验独立目录，robust v2 / multi-adv v2 的 TB 均按时间戳+seed 分子目录，但 ckpt 仍按 save-dir 区分。
2. **resume 续训**：robust v2 与 multi-adv v2 都支持 `--resume latest`，中断后可从最大 update 的 ckpt 继续（含训练统计与课程历史）。
3. **奖励版本**：multi-adv v2 必须用 `--reward-version v2`（默认）；v1 路径不发放 cut_in/blocking 对抗奖励，对抗 agent 只剩零和项可学。
4. **对照公平性**：A/B 组消融时，除被消融项外所有超参（updates / rollout / seed）必须一致，否则结论不可比。
5. **统计显著性**：核心结论（RQ1/RQ2）至少 3 seed；effectiveness 差值建议报告均值±标准差。
6. **hold-out 场景（可选）**：当前场景训练/测试共用。若要支持 RQ1 的真正 hold-out，把部分场景移到独立目录，训练时不纳入 `data/training_scenarios/`，评估时用 `--test-scenario-dir` 指定。

## 10. 远距收敛性修复（2026-06-01）

**问题**：训练中离终点近的车能到达，远 spawn 的车一直没有冲终点的趋势。

**根因**（长 horizon 信用分配 + 奖励塑形对远车不利，三因素叠加）：
1. 所有车共享同一终点，但 `proximity_factor` 让"越近每米 progress 越值钱"（近车 ×2.5、远车 ×1.0）→ 结构性奖励近车；
2. `gamma=0.99` 有效视野仅 ~100 步，终点 +100 对需几百步的远车被折到 ≈0；
3. `step_penalty=-0.5` 对远车是"距离重税"，多跑几百步累计 −200~−400，而 +100 又拿不到 → 远车最优策略变成慢慢挪。

**已实施修复**（不动训练算法，仅奖励常数 / γ / 课程）：

| 方案 | 改动 | 文件 |
|---|---|---|
| ① 距离课程 | 新增 `scenario_dist_{30,50,70,90}m.json`；课程改为按距离升序分 3 段（近→远），近 spawn 先学会冲终点再拉远 | `data/training_scenarios/`、两个训练脚本的 `CurriculumLearning._build_default_stages`（识别 `dist_<N>m` 自动启用，向后兼容） |
| ② progress 距离无关 | `PROXIMITY_BOOST` 1.5 → 0（progress 干净势能塑形，远近一视同仁） | [`carla_multi_agent_env.py` `_compute_rewards_v2`](../environment/carla_multi_agent_env.py#L1290) |
| ② step 惩罚降档 | `step_penalty` −0.5 → −0.1（仍满足 撞车−300 < 不动−100 < 正常行驶） | [`carla_multi_agent_env.py`](../environment/carla_multi_agent_env.py#L1417) |
| ③ 提高 gamma | `--gamma` 默认 0.99 → **0.997**（有效视野 ~100→~330 步，终点奖励能反传到远车早期动作） | robust v2 / multi-adv v2 `build_parser` |

> 未做方案 ④（放大 goal_zone）：会改变 success 判定，导致与历史 run / 对抗评估不可比，故保留终点判定不变。

**验证要点**：
- 分 agent 看 `episode/return_agent_*`：修复后远 spawn agent 的 return / success 应开始追平近车；
- 看 `scenarios/scenario_dist_90m/success_rate_window` 是否随课程推进往上走；
- 高 gamma 下盯 `ppo/explained_variance` 不要崩（Critic 拟合更长 return 更难）。

**对实验计划的影响**：A 组命令无需改（gamma 默认已更新、dist 场景自动进课程）；若想对照"修复前 vs 后"，可加 `--gamma 0.99` 并临时移走 dist 场景复现旧行为。

## 11. "原地不动 farm 奖励" 致命 bug 修复（2026-06-02）

**问题**：近距离训练时策略收敛到"停在原地不动"来刷奖励，不再冲终点。

**根因**：`_compute_rewards_v2` 里 `centering_reward`(最高 +0.5) 和 `yaw_reward`(最高 +0.15) 是**每步无条件发放的"姿态奖励"**——只要车停在车道中央、车头对准目标就给，与是否移动无关。而 `speed_reward` / `alive_bonus` 已做 speed 门控，唯独这两项没有。一辆停着的、居中且对准的车每步净拿：

```
centering(+0.5) + yaw(+0.15) + step(-0.1) = +0.55/step  → 1000 步 farm +550
```

于是"原地不动"成了局部最优。（注：即便用旧的 `step_penalty=-0.5`，停车每步仍 +0.15 > 0，所以这个 bug 早于 §10 的改动就存在，−0.1 只是放大了它。）

**修复**：给 `centering_reward` 与 `yaw_reward` 乘上**运动门控** `motion_gate = min(1, speed/2)`（与 `alive_bonus` 同一 2 m/s ramp）。

| 状态 | 修复前 /步 | 修复后 /步 |
|---|---|---|
| 停在中央对准目标 | **+0.55**（farm） | −0.1（只剩 step 惩罚，严格劣于行驶） |
| 8 m/s 居中行驶 | ≈ +5.3 | ≈ +5.3（姿态奖励照常） |

文件：[`carla_multi_agent_env.py` `_compute_rewards_v2`](../environment/carla_multi_agent_env.py#L1311)（`motion_gate` 定义 + centering/yaw 各乘一次）。

**验证要点**：
- `reward/centering`、`reward/yaw` 分量在早期不应在 `episode/avg_length` 撑满（=超时不动）的同时还为正；
- `episode/rate_timeout` 应下降、`episode/avg_length` 不应顶着 max_steps；
- TB `episode/return_*` 为正必须伴随 `episode/rate_success_to_goal` 上升，而不是长时间不动刷出来的正 return。
