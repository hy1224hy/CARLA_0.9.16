| 项       | 说明                                              |

## 3. 已有 multi-adv 代码的关键设计

[train_multi_adversarial_mappo.py](../training/train_multi_adversarial_mappo.py) 的核心逻辑：

```
合作团队 (cooperative_ids = 0..N-1)
  · 从 pretrained_ckpt 加载，frozen，deterministic 推理
对抗团队 (adversarial_ids = N..N+M-1)
  · 各自一个 Actor（用预训练权重初始化）
  · 共享一个 CentralizedCritic
  · Critic 输入：env.get_adversarial_global_state() = 19 × M 维（只看对抗团队 obs）

Rollout（rollout_steps=1024 步进式）
  for each step:
    合作 actor → deterministic action
    对抗 actor → sample_action (stochastic)
    env.step(joint_action)
    for each adv agent:
      combined_reward = env_adv_reward + coef × (-avg_coop_reward) × 0.01
      buffer.add(...)

PPO 更新（关键设计）
  joint_rewards[t] = Σ adv_agent reward          ← 团队联合奖励
  joint_dones[t]   = max(adv_agent dones)
  joint_adv, joint_ret = compute_gae(joint_rewards, global_values, joint_dones)
  joint_adv = 标准化
  for each adv agent:
    per_agent_tensors[aid] = { obs, act, old_logp, adv: joint_adv }   ← 共享 advantage
  PPO ε-clip 更新各自 Actor，共享 Critic
```

**优点**：
- CTDE 结构清晰，与 robust v2 设计一致
- 用预训练权重初始化对抗 agent，避免从零冷启
- 课程学习（warmup → ramp-up 对抗系数）已就位

## 4. 已有实现的缺陷

按"必须修 → 应该改 → 可以延后"排序。

### 4.1 🔴 信用分配过粗：所有对抗 agent 共享同一 advantage

**位置**：[train_multi_adversarial_mappo.py:370-392](../training/train_multi_adversarial_mappo.py#L370-L392)

```python
joint_rewards[t] = Σ d.reward       # 团队联合奖励
joint_adv, _ = compute_gae(joint_rewards, ...)
for aid in adv:
    per_agent_tensors[aid]["adv"] = joint_adv    # 共享同一 advantage
```

**问题**：MAPPO 的标准做法是"集中 Critic 估 V，但每个 agent 用自己的 reward 序列算 advantage"。共享 advantage 等于把团队奖励直接分给每个 agent，**完全无法学到"agent 2 这一步贡献大、agent 3 那一步在摸鱼"这种内部分工**。

**影响**：当 M ≥ 2 时，对抗 agent 容易学到同质化策略（都去做"切入"或都去"阻挡"），缺乏配合。

**建议改法**：
- 方案 A（简单）：每个 agent 用自己的 reward 序列算 GAE，Critic 仍共享
- 方案 B（标准 MAPPO）：用 Critic 算 `V(global_state)`，但 advantage 用 `A_i = R_i + γV(s') - V(s)`（每个 agent 自己的 reward）
- 方案 C（COMA）：counterfactual baseline，需要新增大量代码

**推荐方案 A** — 改动小，直接对齐 [robust v2](../training/train_no_rllib_mappo_robust_v2.py) 的做法。

---

### 4.2 🔴 Critic 看不到合作团队，价值估计有偏

**位置**：[carla_multi_agent_env.py:1562-1566](../environment/carla_multi_agent_env.py#L1562-L1566) + [train_multi_adversarial_mappo.py:247](../training/train_multi_adversarial_mappo.py#L247)

```python
def get_adversarial_global_state(self):
    features = [obs[aid] for aid in self.adversarial_agent_ids]   # 只有对抗 agent
    return np.concatenate(features)
```

**问题**：Critic 学的是 `V(对抗 obs 拼接)`，根本没看到合作 agent 在哪、速度多少。但对抗策略的最优行为强烈依赖合作 agent 的状态（要切入要先知道目标在哪）。

**影响**：Critic 价值估计偏差大 → GAE 噪声大 → 训练慢且不稳。

**建议改法**：直接复用 [`get_global_state`](../environment/carla_multi_agent_env.py#L1556-L1560)（全员 obs 拼接），输入维度 = `19 × total_agents`。Critic 看到完整全局信息是 CTDE 的标准做法。

---

### 4.4 🟠 合作团队冻结 → 对抗 agent 只学到"过拟合特定合作策略"

**位置**：[train_multi_adversarial_mappo.py:172-183](../training/train_multi_adversarial_mappo.py#L172-L183)

预训练 actor `requires_grad = False` 后从不更新。对抗 agent 训出来的策略是针对**这一个特定 ckpt** 的最佳响应——一旦合作 agent 重训，对抗 agent 大概率失效。

**建议**：Phase D 引入 **co-evolution / iterative training**：
```
for k in 0..K:
  freeze adversary → train cooperative (M updates) 用 robust v2
  freeze cooperative → train adversary (N updates)  用本脚本
  评估当前对抗强度并记录
```

---

### 4.5 🟠 奖励组合的硬编码 magic number

**位置**：[train_multi_adversarial_mappo.py:302](../training/train_multi_adversarial_mappo.py#L302)

```python
combined_reward = base_adv_reward + current_adversarial_coef * (-avg_coop_reward) * 0.01
```

那个 `0.01` 没有任何注释或参数化。`adversarial_coef` 默认 1.0，再乘 0.01 后实际零和项权重是 0.01——和文档/直觉里"零和"语义完全不符。

**建议**：
- 把 `0.01` 提为 CLI 参数 `--zero-sum-scale`
- 或者：把 `adversarial_coef × 0.01` 合并为一个直接参数 `--zero-sum-coef`
- 增加 TB 记录：`reward/adv_base` 和 `reward/zero_sum_term` 分别记录，便于调比例

### 4.8 🟡 起点分配只考虑 cooperative + adversarial 各 1 套

[carla_multi_agent_env.py:340-386](../environment/carla_multi_agent_env.py#L340-L386) 的角色分配逻辑里，合作车 20-50%、对抗车从 40% 起。当 `M ≥ 3` 时，多个对抗 agent 容易堆在同一段路上的 waypoint，触发 spawn 冲突 retry。

**建议**：用更稳健的分配（合作均匀分布在前半段，对抗均匀分布在后半段），或在 JSON scenario 里显式指定每个 agent 的起点。

### 4.9 🟡 没有针对场景多样性的训练

[train_multi_adversarial_mappo.py](../training/train_multi_adversarial_mappo.py) 不调用 `env.set_scenario`，每个 episode 都用默认直道起点。继承了 [实验流程与缺陷分析.md §4.3](实验流程与缺陷分析.md) 里"训练集=测试集"的全部问题。

**建议**：训练时复用 robust v2 的场景采样 + 课程学习管线。

### 4.10 🟡 Done 信号在团队层面被聚合，丢失个体信息

[train_multi_adversarial_mappo.py:367](../training/train_multi_adversarial_mappo.py#L367)

```python
joint_dones[t] = max(joint_dones[t], d.done)
```

任一对抗 agent done 就把团队整体当 done。但其实合作 agent 撞了之后，对抗 agent 应该继续。当前 [`_check_dones`](../environment/carla_multi_agent_env.py#L1373-L1449) 严重碰撞时全员 done，对抗团队的 GAE 跨 episode 信号变得很短。

**建议**：和 [实验流程与缺陷分析.md §4.2](实验流程与缺陷分析.md) 一起改——把 collision 引发的 done 视为 truncation，bootstrap 用 Critic 估计。

### Phase D：Co-evolution 训练循环（3-5 天，进阶）

**目标**：让对抗 agent 不再过拟合某个固定合作策略。

**任务清单**：
- [ ] 实现 [`training/train_coevolution.py`](../training/) 作为顶层调度脚本：
  ```python
  for k in range(num_iterations):
      # Step 1: 冻结对抗，训练合作
      run_robust_v2(adversary_ckpt=current_adv_ckpt, base_ckpt=current_coop_ckpt, updates=M)
      current_coop_ckpt = best_ckpt(...)
      # Step 2: 冻结合作，训练对抗
  ```

**通过标准**：随 iteration k 增加，对抗效力曲线呈上升或震荡上升（不应单调下降，否则说明 co-evolution 失败）。

## 6. 关键设计决策清单（需先和导师对齐）

写代码前先把这些定下来：

| 问题 | 选项 | 推荐 | 理由 |
|---|---|---|---|
| 对抗 agent 数量 M | 2 / 3 / 4 | **从 2 开始** | 先验证算法，再扩规模 |
| 合作 agent 数量 N | 2 / 3 | **2**（保持现状）| 与现有预训练 ckpt 兼容 |
| 对抗团队 advantage | joint / per-agent / counterfactual | **per-agent** | MAPPO 标准做法 |
| Critic 输入 | adv-only / global | **global** | CTDE 标准做法 |
| 对抗 reward 公式 | 现有 `env_adv + zs·0.01` / 重新设计 | **现有**+`--zero-sum-coef` 参数化 | 先跑通再调权重 |
| 是否做 co-evolution | 是 / 否 | **是**（Phase D）| 论文/答辩有亮点 |
| 评估"对抗有效性" | success_rate 差 / return 差 / 完成时间差 | **success_rate 差 + 完成时间差** | 双指标更全面 |
| 终止策略 | 任一碰撞全员 done（现状）/ truncation 语义 | **truncation 语义** | 与 [§4.10](#410--done-信号在团队层面被聚合丢失个体信息) 一起改 |

## 7. 里程碑与时间估算

| Phase | 工作量 | 关键产出 | 依赖 |
|---|---|---|---|
| **A**：基础修复 + v2 移植 | 3-4 天 | `train_multi_adversarial_mappo_v2.py` 可跑 | 无 |
| **B**：评估脚本 + 基线 | 2 天 | `evaluate_multi_adversarial.py` + 对比表 | A |
| **C**：场景化训练 | 2-3 天 | 多场景对抗 ckpt | A, B |
| **D**：Co-evolution | 3-5 天 | `train_coevolution.py` + 对抗强度曲线 | A, B, C |
| **E**：分工分析 | 2 天 | 行为分析图表 | A 完成且训出 ckpt |
| **F**：消融实验 | 3-5 天 | 5 组对照实验数据 | A, B 全部完成 |

**总计**：15-21 天（约 3 周专注开发）

**最小可发表节奏**：A + B + C + F（约 10-13 天）就够支撑一份完整的"多对抗 MAPPO 在 CARLA 直道上的效果"实验报告。

**论文亮点节奏**：再加 D 和 E，能讲"co-evolution + 团队分工"的故事。
